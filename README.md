# Recruiter Bot — надёжная версия

Это переработанная версия Discord-бота для управления сменами рекрутеров, отчётами, инвайтами, финансами, целями и статистикой.

Главная цель этой версии — не просто «чтобы команды работали», а чтобы критические данные не могли сохраниться наполовину, двойное нажатие не выполняло операцию дважды, а после перезапуска бот продолжал нормально работать со старыми сообщениями и существующей БД.

## Требования

- Python 3.10+
- Discord bot token
- заполненные ID сервера, ролей и каналов в `.env`

## Установка

### Windows

```powershell
py -3.10 -m venv .venv
.venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r requirements.txt
copy .env.example .env
python main.py
```

### Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
cp .env.example .env
python main.py
```

После копирования `.env.example` обязательно заполните токен и все ID. При отсутствии обязательной настройки бот теперь останавливает запуск с понятной ошибкой вместо тихой работы с ID `0`.

## Обновление существующего бота

Перед первым запуском новой версии:

1. Полностью остановите старого бота.
2. Сделайте резервную копию текущего `recruiter_bot.db`.
3. Если рядом остались `recruiter_bot.db-wal` и `recruiter_bot.db-shm`, не копируйте работающую базу «на горячую». Сначала остановите старый процесс.
4. Сохраните старую папку проекта целиком как резервную копию.
5. Перенесите ваш `.env` в новую папку и добавьте отсутствующие настройки из `.env.example`.
6. Поместите старый `recruiter_bot.db` в новую папку, если `DATABASE_PATH` не указывает другой путь.
7. Запустите новую версию.
8. Сразу выполните `/админ здоровье`.
9. Выполните `/финансы сверить исправить:false`.
10. Если сверка показывает старый рассинхрон кеша, после проверки журнала используйте `/финансы сверить исправить:true`.

Миграция добавляет недостающие поля и индексы и сохраняет существующие данные. Перед первой миграцией базы со старой схемой автоматически создаётся файл вида `recruiter_bot.db.pre_v2_YYYYMMDD_HHMMSS.db` (если `AUTO_MIGRATION_BACKUP=true`). Версия схемы хранится в `PRAGMA user_version`.

## Что удалено из старой архитектуры

Эти старые Cogs **не нужно переносить в новую папку**:

- `logging.py`
- `notifications.py`
- `weekly_stats.py`

Они использовали старые таблицы `shift_assignments` / `reports` или дублировали новую логику.

## Защита данных

Критические операции выполняются в транзакциях `BEGIN IMMEDIATE`:

- запись на смену;
- начало/завершение смены;
- создание и повторная отправка отчёта;
- одобрение/отклонение отчёта;
- снятие со смены и отмена смены;
- начисление и выплата денег;
- принятие/отклонение инвайта.

При исключении транзакция откатывается целиком.

Для действий, которые могут быть нажаты двумя пользователями одновременно, UPDATE выполняется с условием на текущий статус и проверкой `rowcount`. Поэтому второй обработчик не должен повторно одобрить один отчёт или инвайт.

## Смены

Основные таблицы:

- `shifts` — сама смена;
- `shift_members` — участники смены;
- `shift_reports` — отчёты участников.

Количество `shifts.slots` — число свободных мест. Захват последнего места выполняется атомарным SQL-обновлением. База также запрещает некорректное разбиение отчёта (`на особняке + самостоятельно > принято всего`).

### Команды рекрутера

- `/смена начать`
- `/смена завершить`
- `/смена исправить` — повторно отправить отклонённый отчёт
- `/смена расписание`

### Команды senior/admin

- `/смена создать`
- `/смена снять`
- `/смена отменить`
- `/смена одобрить` — резервный способ по ID отчёта
- `/смена отклонить` — резервный способ по ID отчёта

В отчёте используются отдельные значения:

- принято всего;
- на особняке;
- самостоятельно.

Бот не принимает отрицательные значения, значения больше общего количества или сумму категорий больше общего количества.

## Инвайты

Отклонённый инвайт с тем же статиком можно исправить и отправить повторно тому же рекрутеру. Уже принятый или pending-статик повторно создать нельзя.

Если сообщение с кнопками проверки было удалено, senior/admin может использовать:

- `/инвайт принять`
- `/инвайт отклонить`

## Финансы

Таблица `finances` является журналом операций и главным источником расчёта баланса.

`users.total_salary` и `users.paid_salary` сохранены как кеш для совместимости, но их можно проверить командой:

```text
/финансы сверить исправить:false
```

и после проверки восстановить из журнала:

```text
/финансы сверить исправить:true
```

Выплата больше доступного остатка блокируется внутри транзакции.

## Уведомления

Перед отправкой уведомление атомарно резервируется в таблице `notifications`.

Это защищает от обычных дублей при параллельных вызовах. Для неудачных отправок хранится статус, число попыток и последняя ошибка. Зависший `pending` может быть повторно обработан после таймаута.

Настройки уведомлений:

```env
MAX_NOTIFICATION_ATTEMPTS=3
NOTIFICATION_PENDING_TIMEOUT_MINUTES=10
```

Для защиты от ошибочного ввода огромной суммы есть верхняя граница одной финансовой операции:

```env
MAX_FINANCE_AMOUNT=1000000000
```

Подберите лимит под реальные правила проекта, а не отключайте эту защиту без необходимости.

## Фоновые задачи

`cogs/tasks.py` запускает:

- напоминания о сменах;
- уведомления об опозданиях;
- отметку пропущенных смен;
- напоминание о незавершённом отчёте;
- напоминание senior о pending-отчётах;
- контроль подозрительно коротких смен;
- недельный отчёт.

Недельный отчёт имеет catch-up: если бот был выключен в момент плановой публикации, при следующем запуске он пытается отправить последний завершённый недельный период и использует системный маркер, чтобы не дублировать публикацию.

## Кнопки после перезапуска

ID смены/отчёта/инвайта встроен в `custom_id` кнопки. Обработчики извлекают ID из interaction, поэтому новые сообщения не зависят от старого объекта Python `View` в памяти.

Для смен также хранится `message_id`. Обновление сообщения выполняется напрямую по ID; сканирование последних сообщений используется только как fallback для старых записей, где `message_id` ещё отсутствует.

## Бэкапы

`/админ бэкап` и автоматический бэкап используют SQLite Backup API.

Временный файл удаляется после отправки. Автоматическая задача бэкапа корректно отменяется при выгрузке Cog.

## Диагностика

Используйте:

```text
/админ здоровье
```

Команда проверяет:

- доступность БД;
- `PRAGMA quick_check`;
- нарушения внешних ключей;
- соответствие финансового кеша журналу операций;
- наличие Discord-сервера, необходимых каналов и ролей;
- работу фоновых циклов.

Логи пишутся в консоль и `bot.log` с ротацией.

## Тесты

Для тестов:

```bash
pip install -r requirements-dev.txt
python -m compileall .
pytest
```

Тестовый набор проверяет:

- создание чистой схемы;
- ключевые UNIQUE-ограничения;
- отсутствие обращений к старым таблицам;
- запуск фоновых loops;
- полный сервисный цикл смены;
- отклонение → исправление → повторное одобрение отчёта;
- защиту финансового остатка;
- отклонение → повторную отправку инвайта;
- миграцию старой непустой БД;
- восстановление зависшего notification reservation.

## Время

`TIMEZONE=system` использует локальное время операционной системы. Если VPS работает не в вашей зоне, задайте IANA-зону, например:

```env
TIMEZONE=Europe/Moscow
```

Важно, чтобы настройка времени была определена до начала реальной эксплуатации и потом не менялась без миграционного плана для уже сохранённых локальных timestamp.

## После первого запуска

Рекомендуемый порядок:

1. `/админ здоровье`
2. `/финансы сверить исправить:false`
3. создать тестовую смену;
4. взять её тестовым рекрутером;
5. начать и завершить;
6. отклонить отчёт;
7. исправить `/смена исправить`;
8. одобрить;
9. проверить `/статистика моя`;
10. проверить `/админ бэкап`.

Если эти сценарии проходят на вашем Discord-сервере, можно переходить к обычной эксплуатации.

## Создание полностью новой базы

1. Полностью остановите бота (`Ctrl+C`).
2. Выполните `python reset_database.py`.
3. Введите `RESET` для подтверждения.
4. Скрипт сохранит старую БД в `database_backups/` и создаст новую пустую схему.
5. После этого запустите `python main.py` и проверьте `/админ здоровье`.

На новом хостинге можно вообще не загружать `recruiter_bot.db`: при первом запуске бот создаст её автоматически. Если файловая система хостинга временная, подключите persistent volume/disk, иначе база исчезнет после redeploy/restart контейнера.

## Админ-панель базы
Администратору доступны команды `/база`:
- `/база пользователь @user` — интерактивная карточка пользователя.
- `/база найти запрос` — поиск по Discord ID, статику или имени.
- `/база статик @user новый_статик` — безопасная правка статика (`CLEAR` очищает поле).
- `/база заметка @user текст` — служебная заметка.
- `/база финоперация id` — просмотр операции из журнала `finances`.

Панель намеренно не даёт вручную менять суммы, статусы смен/отчётов и удалять записи. Для таких операций используются профильные команды бота, чтобы сохранялись транзакции, аудит и целостность данных.

# Проверки Recruiter Bot v6.1

Дата: 03.10.2026. Рабочая копия создана отдельно от исходной папки.

## Проверка исправления v6.1

- Всего **236 тестов прошли**; прежние 108 сценариев и 128 дополнительных.
- Python 3.11.17, disnake 2.12.1, aiosqlite 0.22.1, pytest 9.1.1.
- В 8 сценариях исходная v6 воспроизвела замену публичного сообщения личным
  ответом. После исправления эти сценарии проходят.
- Использованы настоящие InteractionResponse и edit_original_response disnake,
  включая сериализацию типов ответов и флага ephemeral; HTTP-адаптер локальный,
  маршрутизирует ответы по правилам Discord и не подключается к сети.
- Проверены успех и отказ при записи, вход и навигация рекламы, ошибки,
  диагностика; публичный оригинал не изменяется личным ответом.
- Проверены кнопки всей основной панели руководства/админки, 25 вложенных
  типов меню, все их дочерние кнопки, формы, проверка рекламы, смен и инвайтов.
- Обычный рекрут получает скрытый отказ, Senior не получает функций Admin.
  Проверка повторяется после снятия роли и при обращении к чужому меню.
- Для Senior/Admin доступ к очереди рекламы сохраняется.
- Восстановление панели проверено по закреплённому сообщению и по истории:
  сообщение редактируется на месте, новая панель не дублируется.
- Очистка личного ответа с карточки смены не меняет записи БД и не удаляет
  штатное упоминание роли. Сообщения других авторов не затрагиваются.
- Настоящий Bot загрузил все 13 cogs без Gateway. Все 44 Python-файла
  разобраны с синтаксисом Python 3.11.
- Проверены совпадение 62 файлов установленной GitHub main со сборкой v6
  и ограничение изменений исполняемого кода тремя файлами cogs.
- Один прежний тест текстового контракта обновлён под обязательный параметр
  with_message=True; проверки доставки и сохранности БД оставлены.
- Discord-сервер и BotHost не подключались к тестам. После установки нужна
  ручная проверка приватного ответа и роли обычного рекрута.

Причина подтверждена кодом SDK и официальной
[документацией disnake](https://docs.disnake.dev/en/stable/api/interactions.html#disnake.InteractionResponse.defer):
у component-взаимодействий режим defer по умолчанию обновляет исходное
сообщение; ephemeral действует при создании отдельного ответа.

## Фактически выполнено

- Исходная сборка до изменений: **65 тестов прошли**.
- Итоговая сборка: **236 тестов прошли** на Windows, Python **3.11.17**,
  disnake **2.12.1**, aiosqlite **0.22.1**, pytest **9.1.1**.
- Исходные 65 тестов сохранены. В трёх тестах миграций обновлены только
  ожидания номера целевой схемы и имени backup с v4 на v6; остальные проверки
  не ослаблены.
- Настоящий aiosqlite импортируется до старого fallback-адаптера. Сервисные
  тесты итоговой версии работают с реальным aiosqlite.
- Отдельные event loops старых тестов получают отдельный asyncio.Lock; это
  настройка тестов, а не замена жизненного цикла production-процесса.
- Синтаксис Python-файлов проверен на совместимость с Python 3.11.
- Все **13 cogs** загрузились в настоящий InteractionBot без Gateway.
  Постоянная панель содержит прежние кнопки и «Реклама».
- Production requirements и Dockerfile остались прежними.

Команда итогового прогона:

```bash
python -m pytest -p no:cacheprovider -o addopts='' -q --tb=short
```

## Новые сценарии

- Запись на смену без статика и использование существующего статика.
- Создание профиля разрешённому участнику при нажатии панели; отказ участнику
  без роли, включая повторную проверку прав после открытия формы.
- Активная смена; отказ обычного подтверждения для другой/законченной смены.
- Десять одновременных подготовок создают одну попытку и один random.
- Границы 20%: 0/19 требуют фото, 20/99 — нет.
- Повторное подтверждение создаёт одну учтённую запись.
- Интервал 3 минуты и невозможность сократить его отменой отметки.
- Требование фото сохраняется после отмены и переподключения БД.
- Нельзя подтвердить чужую попытку или выбранную проверку без фото.
- Фото не увеличивает зачтённый итог до одобрения.
- Запрет собственного одобрения и одновременного двойного решения.
- Обязательная причина отклонения; финансы не меняются.
- Отклонение не переигрывает уже сделанный следующий выбор.
- SHA-256 запрещает точный повтор фото после очистки карточки.
- Одна передача фото для попытки; проверка маркера завершения/освобождения.
- Размер и формат файла проверяются до отправки в Discord.
- Настоящий FileUpload → Label и разбор ModalInteraction в disnake.
- Кнопка открывает форму без зависимости от callback-кеша процесса.
- Фото отправляется одним сообщением, локальные файлы не создаются.
- Потеря ответа Discord сохраняет попытку и не засчитывает её.
- Восстановление передачи: карточка найдена / достоверно отсутствует /
  Discord временно недоступен.
- Без вложения одобрение запрещено.
- Очистка удаляет только старую проверенную карточку бота, сохраняя pending.
- После удаления фото статистика и хеш остаются.
- Периоды, привязка к смене и рейтинг.
- Поле рекламы в отчёте обновляется без дублирования.
- Публичный или совмещённый рабочий канал для фото запрещён.
- Оба способа открытия профиля содержат рекламу за всё время, сохраняя прежние поля.
- Еженедельный отчёт использует точные границы своей недели, включая отправку
  пропущенного отчёта. Проверены начало/конец периода, UTC и Europe/Moscow.
- Сбой отправки недельного отчёта допускает повтор; успешный отчёт не дублируется.
- Цель «Рекламы» учитывает ранее выполненную работу, одобрение фото и отмену
  обычной отметки. Ожидающие и отклонённые фото не увеличивают прогресс.
- Проверены день, неделя, месяц; учитывается время фиксации публикации,
  а не подготовки попытки или проверки фото.
- Замена цели рекламы сохраняет цель по людям и историю; удаление работает
  прежним механизмом. Прогресс виден через кнопки и резервную команду.
- Кнопочная форма ставит цель рекламы и повторно проверяет роли автора и рекрутера.
- Обе проверки здоровья принимают новый тип цели и схему v6.

## Миграция

Использован fixture полной исходной схемы v4 с записями во всех прежних
таблицах: users, shifts, shift_members, shift_reports, finances, invites,
goals, blacklist, logs, notifications.

После миграции проверено равенство всех прежних строк; схема v6;
quick_check = ok; отсутствие ошибок foreign_key_check. Предмиграционный backup
содержит прежнюю схему v4 и данные. Повторный запуск не создаёт новый такой
backup. БД более новой схемы не понижается.

Дополнительно проверено расширение старого CHECK целей на схемах v4 и v5:
сохранение всех строк, существующих реклам, произвольного индекса и триггера,
восстановление счётчика ID даже после удаления записи с наибольшим ID,
создание цели рекламы и прежний запрет неизвестного типа.
При искусственном сбое восстановления индекса перестройка goals откатывается:
прежняя таблица и строки остаются, номер схемы не повышается, временной таблицы нет.

Это проверки на копиях и тестовых данных. Рабочая БД хоста не предоставлялась
и не открывалась.

## Ограничения проверки

Тесты проверяют сервисы, SQL, построение компонентов и смоделированные ответы
Discord. Они не заменяют проверку настоящего клиента, фактических прав канала,
сетевой доступности и настроек конкретного хоста.

Не выполнялись подключение к рабочему Gateway, публикация в вашем Discord,
изменение ролей/каналов, deployment, удаление реальных фото и перезапуск хоста.
В архиве нет токена, рабочей БД, виртуального окружения или тестового Python.
Перед эксплуатацией выполните короткий сценарий из DEPLOY_CHECKLIST_RU.md.

Абсолютное отсутствие ошибок в любой внешней среде гарантировать нельзя.
Пройденные проверки, backup и порядок отката дают конкретные основания
для безопасного обновления.

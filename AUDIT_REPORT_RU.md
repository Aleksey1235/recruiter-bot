# Финальный аудит Recruiter Bot — Production Ultimate Audited

Дата: 2026-08-25  
Схема БД: v4  
Python: 3.11  
Основной интерфейс: кнопочная панель + slash-команды как резерв

## Что перепроверено

- создание, бронирование, ранний старт, завершение, самостоятельный выход и снятие со смены;
- многоместные и ночные смены;
- защита от пересекающихся смен и нескольких active-смен одного рекрутера;
- поведение общей смены после старта, завершения/снятия последнего участника и истечения времени;
- отчёты: pending → approved/rejected → исправление → повторная проверка;
- отказоустойчивость карточек Discord: успешная запись в БД больше не выдаётся за ошибку только из-за сбоя редактирования сообщения;
- резервные approve/reject по ID;
- инвайты, чек-лист, повторная проверка ЧС при approve;
- ЧС по Discord ID и статику, история, снятие только Admin, дополнение доказательства/заметки;
- защита SQLite от ошибочных сверхбольших числовых Discord ID;
- финансы, двойная выплата, нормализация сумм, отрицательный баланс, сверка кеша;
- цели и стартовый прогресс цели, поставленной в середине текущего периода;
- статистика, локальные периоды и недельные финансы;
- уведомления, системные маркеры, retries и недельный отчёт;
- автобэкап и защита от дубля после рестарта контейнера;
- миграции старых БД до schema v4 с предмиграционным backup;
- `/админ здоровье` и расширенная диагностика базы;
- права Recruiter / Senior / Admin на каждом интерактивном шаге;
- кнопочная помощь и повторная проверка ролей после открытия меню;
- постоянная панель: сначала ищется закреплённая карточка, затем history fallback;
- отсутствие зависимости от prefix/message-content intent: используется `InteractionBot`.

## Новые защиты финального аудита

1. **Discord ID overflow guard.** Очень длинная числовая строка не передаётся в SQLite INTEGER и не может вызвать `OverflowError`.
2. **Blacklist audit trail.** Ранний блок инвайта в панели использует тот же сервисный pre-check и записывает попытку в audit logs.
3. **Blacklist details.** Только Admin может добавить или дополнить существующую запись доказательством/заметкой без удаления истории.
4. **Состояние смены после старта.** Смена не возвращается в ложный `open`, когда запись по времени уже закрыта.
5. **Ambiguous start guard.** При повреждённых legacy-данных с несколькими одновременно стартуемыми сменами бот не выбирает случайную запись.
6. **Delivery vs DB state.** Ошибка ЛС/редактирования Discord-карточки не откатывает уже корректно выполненную транзакцию; пользователю показывается точный статус.
7. **Card link fallback.** Если карточка отправлена, но `message_id` не удалось записать, карточка не считается потерянной: custom ID/footer позволяют восстановить связь позже.
8. **Control-channel fallback.** Если отчёт/инвайт сохранён, но публичная карточка не создана, бот пытается уведомить senior в канале контроля.
9. **Goal initial progress.** Новая цель на текущий день/неделю/месяц сразу получает уже достигнутый прогресс периода.
10. **Daily backup marker.** Перезапуск хоста не создаёт бесконечные одинаковые автобэкапы; неудача может быть повторена.
11. **Expanded health.** Диагностика показывает конкретные `SHIFT`, `MEMBER`, `REPORT`, `BLACKLIST`, `FINANCE`, `NOTIFY` ID/связи вместо только общего числа ошибок.
12. **Panel deduplication.** Постоянная панель ищется среди pinned messages до history fallback.

## Автоматическая проверка

Финальный набор: **65 тестов**.

Покрываются:

- schema/migrations;
- транзакции и конкурентные операции;
- смены и отчёты;
- инвайты и ЧС;
- финансы;
- цели;
- статистика;
- уведомления;
- health/diagnostics;
- статические архитектурные контракты UI.

Дополнительно весь Python-код парсится с `ast` в режиме **Python 3.11** и проходит `compileall`.

Точные production-зависимости проверены по PyPI на дату сборки: `disnake 2.12.1`, `aiosqlite 0.22.1`, `python-dotenv 1.2.3`, `tzdata 2026.3`; `disnake 2.12.1` заявляет поддержку Python 3.11.

В изолированной среде сборки доступ к PyPI и живому Discord Gateway отсутствует, поэтому сетевой interaction-smoke-test выполняется уже после deployment. Изменённые API (`InteractionBot`, `Loop.add_exception_type`, `TextChannel.pins`) сверены с документацией disnake 2.12.

## Обязательный smoke-test после deployment

1. `/админ здоровье` — все пункты должны быть `✅ OK`.
2. Проверить отдельный канал панели: после restart не появляется вторая панель.
3. Создать тестовую смену на 2–3 места → два рекрутера записываются → один стартует раньше → до официального начала второе место остаётся доступным.
4. Проверить выход booked-рекрутера и возврат свободного места.
5. Завершить смену → reject отчёта → исправить → approve.
6. Создать обычный инвайт → approve.
7. Добавить второго тестового пользователя в ЧС → новый инвайт блокируется.
8. Создать pending-инвайт, затем добавить человека в ЧС → approve блокируется без начисления.
9. Проверить права ЧС: Senior не видит/не использует управление ЧС; Admin добавляет, дополняет, ищет, просматривает историю и снимает только с обязательной причиной.
10. Проверить `/админ бэкап` и наличие автоматического бэкапа в канале логов.

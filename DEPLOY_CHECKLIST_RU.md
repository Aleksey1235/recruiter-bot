# Безопасное обновление Recruiter Bot до v6

Код подготовлен отдельно. Работающий хост, его окружение и рабочая БД не
использовались. Ниже порядок действий, а не уже выполненное развёртывание.

## До остановки

1. Выберите время без активной работы рекрутеров.
2. Сохраните точную старую версию кода, образ или commit для отката.
3. Выполните **Админ → Бэкап** и скачайте файл. Прежняя команда
   `/админ бэкап` также остаётся резервным способом.
4. Сохраните прежнее окружение в закрытом месте. Не публикуйте токен.
5. Уточните фактический DATABASE_PATH и рабочую директорию. Путь по умолчанию
   относительный: `data/recruiter_bot.db`.
6. Проверьте постоянный диск/volume: каталог БД не должен исчезнуть при Rebuild.
   Dockerfile сам не создаёт подключение постоянного хранилища.
7. Проверьте свободное место: перед миграцией потребуется место под ещё одну
   копию БД. Фото новой системы занимают хранилище Discord, не диск хоста.

## Канал проверки рекламы

Создайте **отдельный текстовый канал**, например `проверка-рекламы`:

- @everyone: View Channel запрещено.
- Обычная роль Recruiter: View Channel запрещено; Manage Messages не выдавать.
- Senior/Admin: View Channel и Read Message History разрешены.
- Бот: View Channel, Send Messages, Read Message History, Embed Links,
  Attach Files разрешены.
- Проверьте остальные роли и персональные разрешения: они не должны открывать
  канал обычным участникам.

Канал нельзя совмещать с каналом смен, обычных отчётов, статистики, контроля,
логов или основной панели. Бот блокирует такое совмещение.

Добавьте на хосте:

```env
ADS_REVIEW_CHANNEL_ID=ФАКТИЧЕСКИЙ_ID_НОВОГО_КАНАЛА
ADS_FAMILY_NAME=DeSanta
ADS_CHECK_PERCENT=20
ADS_INTERVAL_MINUTES=3
ADS_RETENTION_DAYS=90
AUTO_MIGRATION_BACKUP=true
```

BOT_TOKEN, GUILD_ID, старые роли/каналы, DATABASE_PATH и TIMEZONE сохраняются.
Не копируйте `.env.example` поверх рабочего `.env`.

## Обновление

1. Полностью остановите старый процесс/контейнер. Одновременно должна работать
   только одна копия бота с этим токеном и этой БД.
2. Обновите код из архива. Не удаляйте и не заменяйте рабочие `*.db`,
   `*.db-wal`, `*.db-shm`, `.env` и постоянный каталог данных.
3. **Не запускайте reset_database.py** — это создание чистой БД, не обновление.
4. Выполните обычный Rebuild, сохранив диск и окружение.
5. Запустите новую версию. Python остаётся 3.11, production requirements
   сохранены. Перед миграцией создаётся `.pre_v6_...db` backup.
6. **Админ → Здоровье**: нужна схема v6, исправные прежние проверки,
   учёт рекламы и канал/фоновая задача рекламы.
7. Если канал не настроен, диагностика прямо сообщает, что реклама выключена.
   Это позволяет сначала запустить прежние функции и закончить настройку.
8. Проверьте кнопку «Реклама» в прежней единственной постоянной панели.

Обновление поддерживает исходную v4 и подготовленную v5. Рабочие рекламы v5
сохраняются. Для нового типа целей миграция расширяет старый CHECK таблицы
goals, сохраняя существующие цели, их ID, историю, индексы и триггеры.
Прямое редактирование номера схемы или удаление таблицы goals не требуется.

При ошибке миграции не удаляйте БД и не запускайте RESET. Сохраните лог,
исходную БД и предмиграционный backup; устраните причину либо выполните откат.

## Короткая проверка в Discord

Используйте тестовых сотрудников/смену и помечайте тестовые записи как тестовые.

1. Новый Recruiter нажимает панель: профиль доступен, статик может отсутствовать.
   Участник без нужной роли не получает доступа.
2. «Взять смену» работает сразу. Проверьте старую карточку, существующий статик
   другого сотрудника и ограничение последнего места.
3. Начните смену. Повторное «Подать рекламу» возвращает ту же попытку. После
   закрытия меню откройте «Текущая попытка».
4. Обычная публикация подтверждается одним нажатием, повтор не увеличивает итог.
   Новая публикация раньше трёх минут блокируется.
5. Для воспроизводимой фото-проверки временно задайте ADS_CHECK_PERCENT=100,
   перезапустите бот и создайте новую тестовую попытку. Настройка влияет только
   на новые выборы, не меняет уже подготовленные попытки.
6. Отмена выбранной проверки не снимает требование фото со следующей попытки.
7. Прикрепите фото кнопкой: в обычном канале сообщения нет, в закрытом — одна
   карточка бота. Она доступна Senior/Admin и недоступна Recruiter.
8. Ожидающее фото не увеличивает зачтённый итог. Другой Senior одобряет его;
   свою рекламу проверять нельзя.
9. Вторую проверку отклоните с причиной. Причина видна в истории рекрутера,
   публикация не засчитана.
10. Перезапустите бот: подготовленная попытка, требование фото и кнопки уже
    отправленной карточки сохраняются.
11. Завершите смену: число рекламы подставлено в отчёт. Проверьте его обновление
    после решения по ожидающему фото.
12. Выполните прежний короткий сценарий инвайта, reject → resubmit → approve
    отчёта и проверку ЧС. Финансовые итоги должны совпадать с прежней версией.
13. Откройте профиль рекрутера: блок рекламы должен совпасть с его итогом за
    всё время. Ожидающие и отклонённые проверки видны отдельно.
14. Через прежнее меню целей поставьте тип «Рекламы» за неделю. В «Мои цели»
    должен быть текущий зачтённый итог; цель по людям или сменам остаётся.
    После одобрения фото повторно откройте цели и проверьте увеличение прогресса.
15. Еженедельный отчёт должен содержать блок рекламы за указанный в нём период.
    На тестовом окружении проверьте также отправку пропущенной недели после
    перезапуска. Ранее отправленные недельные отчёты не обновляются задним числом.
16. Верните ADS_CHECK_PERCENT=20. Проверьте здоровье и скачайте новый backup.

Не уменьшайте срок хранения на рабочем фотоархиве ради проверки очистки:
выбор и удаление проверены тестами. Дополнительные проверки — на тестовой БД.

## Откат

До начала обычной работы новой версии:

1. Остановите новую версию.
2. Сохраните её БД отдельным согласованным backup для диагностики.
3. Верните прежний код/образ и окружение.
4. Восстановите **вместе с ним** backup до обновления либо `.pre_v6_...db`.
   Не запускайте старый код на БД v6: он не знает новую схему и может переписать
   её номер.
5. WAL/SHM новой БД не должны оставаться рядом с восстановленным файлом. Сначала
   полностью остановите процесс, сохраните комплект файлов, затем замените
   его согласованным backup. Не копируйте один `.db` из работающего WAL.
6. Запустите старую версию, проверьте здоровье, панель и последние данные.

Если в новой версии уже появились реальные операции, старый backup их не
содержит. Сначала остановите работу, сохраните новую БД и подготовьте перенос
новых операций. Безусловный автоматический откат после начала эксплуатации
в этот выпуск не добавлен.
